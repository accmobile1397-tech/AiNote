# My Project Extended Knowledge Preferences
## Version 3.0 — Agentic SDLC / AI Native Software Factory Patterns

**Status:** Canonical successor to v2.2

## 1. Purpose

This document contains reusable patterns, practices and workflows accumulated for future AI-native projects. It complements My Project Preferences, which contains defaults and principles.

## 4. Agent-Agnostic Project Memory

Project-owned memory is durable; Agent memory is transient.

```text
General Knowledge
→ Project Bootstrap
→ Project Knowledge
→ POM / Project State
```

Agent replacement must not cause context loss.

## 5. Foundation Gate Pattern

After discovery, generate the six-document baseline:
- Project Context
- Vision
- Product Definition
- Domain Model
- Requirements Baseline
- Architecture Baseline

PO approval at this point authorizes autonomous documentation.

## 6. Autonomous Documentation Factory

Documentation should be generated by a versioned Skill that can determine dependencies, create the next artifact, validate consistency, update state and resume after interruption.

The goal is not to manually write every document; it is to build a reliable document-generation and maintenance system.

## 7. Documentation Validator Pattern

Independent validator checks:
- missing documents
- missing dependencies
- contradictions
- unresolved ambiguity
- incomplete requirements
- incomplete contracts
- untestable acceptance criteria
- task-generation viability
- traceability
- SDLC compliance
- developer readiness

Failure loops back to documentation.

## 8. Specification-to-Execution Pattern

```text
Intent
→ Requirement
→ Domain / Architecture
→ Feature Specification
→ Task
→ Code
→ Test
→ Evidence
→ Review
```

Every code change must be traceable to a task and every task to an approved specification.

## 9. Specification Graph Pattern

Maintain machine-readable or referenceable relationships between intent, requirements, architecture, specifications, tasks, code, tests and evidence. This enables impact analysis and prevents orphaned implementation.

## 10. Project State / Resume Pattern

State is persistent and machine-readable. A new Agent must be able to identify current phase, current task, approvals, workflow mode, blockers and next action from Repository state.

## 11. Multi-Roadmap Pattern

- Master Roadmap: lifecycle-level view
- Phase Roadmap: created by the responsible phase executor
- Task Plan: executable work

Do not over-specify future phases prematurely.

## 12. PO Non-Blocking / Governance Pattern

Human governance remains explicit, but Human should not be a bottleneck for every micro-task. After a defined approval gate, execution can proceed autonomously.

## 13. Runtime Workflow Mode Pattern

Two modes:
- Gated: task-by-task approval
- Autonomous: approved queue continues

PO can switch modes during execution. The project state remains continuous.

## 14. Agent Handover Pattern

```text
Agent A
→ Persist State / Report / Evidence
→ Agent B
→ Read Repository
→ Resume
```

No handover message should be the sole source of continuity.

## 15. UI Engineering Pattern

For web projects, UI is part of the specification and implementation contract. Agents should be capable of producing:
- forms
- cards
- dashboards
- charts
- tables
- filters
- navigation
- landing pages
- settings
- wizards
- responsive layouts
- loading/empty/error/success states

Default Persian project UX: mobile-first, RTL, Jalali-aware, Vazirmatn, accessible and responsive.

## 16. AI Architecture Patterns

Keep Application dependent on AI Capabilities, not providers. Keep LLM and Embedding separate. External AI Gateways remain replaceable through stable contracts. RAG lifecycle and embedding versioning are explicit.

## 17. Knowledge Evolution

```text
Execution
→ Feedback
→ Lesson
→ Pattern Candidate
→ Review
→ Reusable Pattern
```

Project-specific knowledge must not pollute the general Pattern Library unless generalized and reviewed.

## 18. Factory Readiness Principle

A project is ready for Coding Developer when the developer can implement the next feature without guessing critical product, domain, architecture, UX, API, data or acceptance behavior.

## 19. Final Principle

> **We do not optimize for more documents. We optimize for a coherent, traceable specification system that any capable Agent can execute.**
